## Automation (v1.0.0 / v2.7.2 / v2.14.0)
- [wow_forecaster/scheduler.py](../../wow_forecaster/scheduler.py) — SchedulerDaemon (stdlib only)
- CLI: start-scheduler (foreground daemon)
- [scripts/setup_tasks.bat](../../scripts/setup_tasks.bat) — registers four tasks, all silent via wscript.exe + run_silent.vbs (vbs waits and propagates the exit code): WoWForecaster-Hourly (hourly, /ST pinned to :16 — daily-collision avoidance + snapshot-edge sampling; also matches the cloud capture's :16 Worker dispatch each hour, #83), WoWForecaster-Daily (07:00), WoWForecaster-HealthCheck (/SC HOURLY /MO 6 /ST 00:45 — 29 min clear of the :16 ingest, done before 07:00), WoWForecaster-Backup (/SC DAILY /ST 07:30 — after the daily forecast so each backup includes that morning's forecasts; issue #80)
- setup_tasks.bat state preservation (v2.7.1, issue #6): schtasks /Create /F recreates tasks ENABLED, so each registration queries the prior state (PS Get-ScheduledTask via `call powershell`, exit 2 = Disabled) and re-disables right after /Create; `if errorlevel 1` threshold = disable-on-uncertainty (call on an unresolvable name yields 1, not 9009); a failed re-disable exits 1 with a disable-manually error; WOWFC_SCHTASKS test seam (tests/test_scripts/test_setup_tasks.py, powershell stubbed via PATH override)
- Wake-to-run (v2.7.2, issue #40): schtasks /Create cannot set WakeToRun, so after each registration setup_tasks.bat flips it by PS fetch-modify-write (`Get-ScheduledTask` -> `.Settings.WakeToRun = $true` -> `Set-ScheduledTask -InputObject`; NEVER New-ScheduledTaskSettingsSet, which resets all settings to defaults including Enabled=true); for a was-disabled task the script re-asserts /Change /DISABLE after the wake-set (belt and braces around the cmdlet round-trip); wake-set failure is fatal (exit 1) and runs after the re-disable so the failure exit leaves the task Disabled; warn-only RTCWAKE power-plan check via WOWFC_POWERCFG seam (AC index must be 0x1; 0x0 Disable and 0x2 Important-only both block schtasks wake timers); machine may sleep between runs, but a powered-off machine does not wake (cloud capture covers that)
- Sleep-back (v2.14.0, issue #78): [scripts/sleep_back.ps1](../../scripts/sleep_back.ps1) — #40 built only the wake half; its Change list delegated re-sleep to Windows' unattended idle timeout, which never applies because the tasks are `Interactive only`, and the 30-minute STANDBYIDLE that covered for it was a temporary #40-acceptance setting returned to Never around 07-26. So in steady state nothing returned the box to sleep and an overnight sleep ended at the first wake timer (measured 30.6 min asleep then 24.5 h awake). Two modes: `-Capture` prints ONLY the `LASTINPUTINFO.dwTime` integer (any log line on stdout poisons the caller's `for /f`); `-Decide` evaluates the window then the four conditions. **Condition 2 is a dwTime EQUALITY check, not an idle threshold**: a threshold reads as idle when input arrived early in a long run (the hourly has hit 43 min) and would suspend the box with the operator at it. Evaluation order is window -> bounds -> lock -> alert -> input -> wake -> other tasks (all ANDed, so order only picks which reason is logged; shared machine state before the operator check). Condition 3 checks `.hourly.lock` as well as task state because a manual `sync-snapshots` drain holds that lock and is not a scheduled task. **Fail-safe bias is INVERTED vs its neighbours** (run_hourly's lock takeover and run_healthcheck's alert window both act on uncertainty): here unevaluable means stay awake, because a wrong sleep interrupts the operator. Suspend is `Add-Type` P/Invoke `SetSuspendState(false,false,false)` — `bDisableWakeEvent` MUST be false or it silently undoes #40, and never `rundll32 powrprof.dll,SetSuspendState 0,1,0`, which passes "0,1,0" to a three-BOOL function as one string and drops the args (the real source of the "it hibernates instead" folklore; this box suspends to S3, verified three ways, so hibernate/Fast Startup are left alone)
- Log entry separator: each of the four scheduled scripts opens a run's entry with a bare 89-char `=` rule, redirection-first (`>> logs\x.log echo ===...`) because cmd keeps the space before a trailing `>>` as part of the echoed text. The rule carries no timestamp on purpose: the previous `[%DATE% %TIME%] ====` form was indistinguishable at a glance from the timestamped lines around it, which is what made entry starts hard to find (hourly.log is 86 MB). **In run_hourly.bat the rule sits ABOVE the lock guard**, unlike the other three, because that guard logs on both paths: below it, a SKIPPED run appends its one line under the previous run's rule and reads as part of that entry, and a TAKEOVER line sits orphaned above its own. Shared constant `ENTRY_SEPARATOR` in tests/test_scripts/conftest.py, asserted as line 1 of a fresh log by one test per script (the hourly skip-path assertion is the load-bearing one)
- Sleep-back call sites + window (issue #78): wired into run_hourly.bat and run_healthcheck.bat only; run_daily.bat (07:00) and run_backup.bat (07:30) deliberately never sleep so the box is up when the operator arrives. **The call is DETACHED (`start "" /b`)**: SetSuspendState does not return until resume and run_silent.vbs waits on the bat, so an inline call would hold the task Running for the whole sleep, and schtasks leaves MultipleInstances at IgnoreNew, so the next trigger could be silently skipped (the 96-day-outage failure class). Spike 2026-07-29 confirmed a `start /b` child outlives task completion by 17s. Window is 20:00-08:00 local and WRAPS midnight (`hour >= from OR hour < until`); a one-sided "refuse at or after 08:00" refuses every evening hour, so a box slept at 22:00 would be woken by the 23:16 hourly and stay up all night. Bounds: `-FromHour`/`-UntilHour` param > `WOWFC_SLEEP_FROM_HOUR`/`WOWFC_SLEEP_UNTIL_HOUR` env > 20/8; garbage refuses and logs, empty means unset (Windows cannot distinguish empty from absent). Decisions append to logs/sleep_back.log. `WOWFC_NO_SLEEP` skips only the suspend (test seam, forced in every test path)

## Durable Backup (v2.9.0, issue #80)
- [wow_forecaster/backup/durable_backup.py](../../wow_forecaster/backup/durable_backup.py) — build_durable_db copies schema from the SOURCE's live sqlite_master (NOT apply_schema: recommendation_outputs carries migration-added columns score/score_components/category_tag/risk_level that schema.py's DDL omits, so INSERT SELECT * into an apply_schema() table would fail on column count; ALTER TABLE ADD COLUMN updates sqlite_master.sql, so it is the true shape); copies data for every table except EXCLUDED_TABLES (the two obs tables, recreated empty so the file is drop-in restorable); reads only the small tables + CREATE text, never scans the 9.7 GB obs tables; no VACUUM; foreign_key_check must pass. run_backup(): build -> gzip(-9) -> prune_local(keep_local) -> upload LAST (so a failed upload still leaves a local .db.gz). upload_backup reuses cloud_fetch._retry, explicit BACKUP_S3_* creds (own scoped token, separate bucket). Key: db_backups/YYYY/MM/DD/durable_<ts>Z.db.gz
- CLI: backup-durable-db (--output-dir/--upload/--no-upload/--keep-local); [backup] config (BackupConfig: output_dir, keep_local=7, upload_enabled, stale_hours=30); BACKUP_S3_* in .env (endpoint/bucket/access_key_id/secret_access_key, region default auto); boto3 from [cloud] extra
- Real snapshot 2026-07-23: 118 MB raw / 31 MB gz, 24 tables, ~718K rows, <6s; forecast_outputs (325K) + daily_rollup_item (333K) dominate, so ~31 MB/day and ~11 GB/yr unbounded (exceeds R2 free tier in <1yr). Each backup is a COMPLETE snapshot, so a bounded bucket lifecycle (100d recommended, ~3 GB) loses no rollups; design + restore steps + retention note: [docs/db-backup.md](../../docs/db-backup.md)
- Alerting: check-data-health --backup-stale-hours N (opt-in, 0=off default) flags newest .db.gz older than N (or none present) via collect_health_report(backup_dir=...); backup_is_stale joins HealthReport.has_failures; run_healthcheck.bat passes 30; run_daily.bat does NOT, so a stale backup never blocks the forecast freshness gate
- Incident runbook (issue #106): docs/integrity-incidents.md; two-pass discriminator for local integrity errors (identical lists = real damage -> restore; differing/clean = transient RAM read -> no DB action), never REINDEX/VACUUM this DB as repair, verify-before-restore, obs rebuild = `sync-snapshots --since <30d ago> --limit 0` (bare run only reaches max_backfill_days=3)
- Off-box verification (issue #104): wow_forecaster/backup/verify.py restores the newest db_backups/ object on a CI runner daily (.github/workflows/verify-backup.yml, 14:00 UTC + dispatch) and runs integrity_check + foreign_key_check + row-count floors (DEFAULT_MIN_ROW_TABLES) + no-shrink vs the previous object (APPEND_ONLY_TABLES: rollups + forecast_outputs); missing/stale newest object (BACKUP_VERIFY_MAX_AGE_HOURS, default 30) FAILS, never skips; read-only BACKUP_S3_* repo secrets, added by hand; `python -m wow_forecaster.backup.verify <file>` verifies a local file pre-restore; verify_backup_db never raises on a bad file (unreadable -> failed VerifyResult); import chain stdlib + lazy boto3 (workflow installs --no-deps)
